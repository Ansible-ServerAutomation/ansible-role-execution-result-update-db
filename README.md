# ansible-role-execution-result-update-db

Ansible role that captures execution results from [ansible-role-execution-result](https://github.com/Ansible-ServerAutomation/ansible-role-execution-result) and stores them in a database for persistent tracking, analytics, and auditing.

## Overview

This role consumes the artifacts generated by `ansible-role-execution-result` and stores them in various database backends including PostgreSQL, MySQL, SQLite, and MongoDB. It's designed to work seamlessly with AWX/Tower or standalone Ansible playbooks.

### Features

- **Multiple Database Support**: PostgreSQL, MySQL, SQLite, MongoDB
- **Dual-Table Design**: Separate tables for successful (`success_jobs`) and failed (`failed_jobs`) executions
- **Automatic Schema Management**: Creates tables/collections automatically
- **Batch Processing**: Efficient bulk inserts
- **Data Validation**: Validates data before insertion
- **Flexible Configuration**: Highly customizable through variables
- **Error Handling**: Graceful failure handling with optional strict mode
- **AWX/Tower Integration**: Works with AWX artifacts and job metadata
- **Field Truncation**: Prevents database errors from oversized fields

## Database Schema

The role automatically creates two separate tables/collections to organize execution results:

### Table: success_jobs

Stores successful execution results (status = 'SUCCESS').

| Column | Type | Description |
|--------|------|-------------|
| `id` | INTEGER/SERIAL | Primary key (auto-increment) |
| `timestamp` | TIMESTAMP/TEXT | Execution timestamp |
| `hostname` | VARCHAR(255) | System hostname |
| `inventory_hostname` | VARCHAR(255) | Ansible inventory hostname |
| `ansible_host` | VARCHAR(255) | Ansible host variable |
| `project` | VARCHAR(500) | AWX/Tower project name |
| `organization` | VARCHAR(500) | AWX/Tower organization |
| `job_template` | VARCHAR(500) | AWX/Tower job template |
| `playbook` | VARCHAR(500) | Playbook filename |
| `scm_url` | VARCHAR(1000) | Git repository URL |
| `scm_branch` | VARCHAR(255) | Git branch |
| `scm_revision` | VARCHAR(255) | Git commit SHA |
| `execution_environment` | VARCHAR(500) | Execution environment name |
| `status` | VARCHAR(50) | Execution status (always 'SUCCESS') |
| `return_code` | INTEGER | Task return code |
| `message` | TEXT | Task message |
| `stdout` | TEXT | Standard output |
| `stderr` | TEXT | Standard error |
| `exception` | TEXT | Exception traceback |
| `warnings` | JSON/JSONB/TEXT | Task warnings |
| `failed_task` | VARCHAR(500) | Name of failed task (usually empty) |
| `failed_task_module` | VARCHAR(255) | Module that failed (usually empty) |
| `os_distribution` | VARCHAR(100) | OS distribution (e.g., Ubuntu) |
| `os_version` | VARCHAR(100) | OS version |
| `os_family` | VARCHAR(100) | OS family (e.g., Debian) |
| `os_system` | VARCHAR(100) | System type (e.g., Linux) |
| `os_architecture` | VARCHAR(100) | Architecture (e.g., x86_64) |
| `created_at` | TIMESTAMP | Record creation time |
| `updated_at` | TIMESTAMP | Record update time |

**Indexes**: timestamp, project, playbook

### Table: failed_jobs

| `message` | TEXT | Task message or error |
| `stdout` | TEXT | Standard output |
| `stderr` | TEXT | Standard error |
| `exception` | TEXT | Exception traceback |
| `warnings` | JSON/JSONB/TEXT | Task warnings |

| `updated_at` | TIMESTAMP | Record update time |

**Indexes**: timestamp, project, failed_task

### Benefits of Dual-Table Design

- **Better Query Performance**: Queries on successful or failed jobs don't need to filter by status
- **Optimized Indexing**: Different indexes for success (playbook-focused) vs failure (error-focused) patterns
- **Simplified Analytics**: Easier to analyze failure patterns separately from success metrics
- **Storage Efficiency**: Failed jobs can store additional error details without impacting success table size

## Usage

### Basic Usage with PostgreSQL

```yaml
- name: Store execution results in PostgreSQL
  hosts: localhost
  gather_facts: true
  
  tasks:
    - name: Include the database role
      ansible.builtin.include_role:
        name: ansible-role-execution-result-update-db
      vars:
        execution_result_db_type: "postgresql"
        execution_result_db_host: "db.example.com"
        execution_result_db_port: 5432
        execution_result_db_name: "ansible_logs"
        execution_result_db_user: "ansible_user"
        execution_result_db_password: "{{ vault_db_password }}"
```

### Using with SQLite (Simplest Setup)

```yaml
- name: Store results in SQLite
  hosts: localhost
  gather_facts: true
  
  tasks:
    - name: Include the database role
      ansible.builtin.include_role:
        name: ansible-role-execution-result-update-db
      vars:
        execution_result_db_type: "sqlite"
        execution_result_db_sqlite_path: "/var/lib/ansible/results.db"
```

### Complete Workflow Example

```yaml
- name: Deploy Application with Result Tracking
  hosts: webservers
  gather_facts: true
  
  tasks:
    - name: Deploy application
      block:
        - name: Update code from Git
          ansible.builtin.git:
            repo: "https://github.com/example/app.git"
            dest: /var/www/app
          register: deploy_result

        - name: Record successful deployment
          ansible.builtin.include_role:
            name: ansible-role-execution-result
          vars:
            execution_result_registered_var: "{{ deploy_result }}"

      rescue:
        - name: Record deployment failure
          ansible.builtin.include_role:
            name: ansible-role-execution-result
          vars:
            execution_result_registered_var: "{{ ansible_failed_result }}"

      always:
        - name: Store results in database
          ansible.builtin.include_role:
            name: ansible-role-execution-result-update-db
          vars:
            execution_result_db_type: "postgresql"
            execution_result_db_host: "{{ db_host }}"
            execution_result_db_name: "ansible_automation"
            execution_result_db_user: "{{ db_user }}"
            execution_result_db_password: "{{ db_password }}"
          run_once: true
          delegate_to: localhost
```

### Using with MongoDB

## Integration with ansible-role-execution-result

This role is designed to work with [ansible-role-execution-result](https://github.com/Ansible-ServerAutomation/ansible-role-execution-result). The typical workflow is:

1. **Execute tasks** in your playbook
2. **Capture results** using `ansible-role-execution-result` (sets the `execution_results` fact)
3. **Store in database** using this role (`ansible-role-execution-result-update-db`)

Example:

```yaml
- block:
    - name: Run critical task
      ansible.builtin.command: /usr/bin/critical_script.sh
      register: task_result
  
  rescue:
    - name: Capture failure
      ansible.builtin.include_role:
        name: ansible-role-execution-result
      vars:
        execution_result_registered_var: "{{ task_result }}"
  
  always:
    # Store captured results in database
    - name: Persist to database
      ansible.builtin.include_role:
        name: ansible-role-execution-result-update-db
      vars:
        execution_result_db_type: "postgresql"
        # ... database configuration ...
```

## Security Considerations

### Password Management

**Never store database passwords in plain text!** Use Ansible Vault:

```bash
# Create encrypted variable file
ansible-vault create vars/db_secrets.yml

# Add password
execution_result_db_password: "your_secure_password"

# Use in playbook
ansible-playbook playbook.yml --ask-vault-pass
```

### SSL/TLS Connections

For production environments, enable SSL/TLS:

```yaml
execution_result_db_ssl_enabled: true
execution_result_db_ssl_ca_cert: "/path/to/ca.crt"
execution_result_db_ssl_client_cert: "/path/to/client.crt"
execution_result_db_ssl_client_key: "/path/to/client.key"
```

### Database Permissions

Create a dedicated database user with minimal required permissions:

```sql
-- PostgreSQL example
CREATE USER ansible_writer WITH PASSWORD 'secure_password';
GRANT CONNECT ON DATABASE ansible_execution_results TO ansible_writer;
GRANT INSERT, SELECT ON TABLE success_jobs TO ansible_writer;
GRANT INSERT, SELECT ON TABLE failed_jobs TO ansible_writer;
```

### Using AWX/Ansible Tower Credentials

For AWX or Ansible Tower environments, leverage native credential management instead of storing database passwords in variables.

#### Creating a Database Credential in AWX/Tower

1. **Navigate to Credentials**: Go to **Resources** → **Credentials** in AWX UI

2. **Create New Credential**: Click **Add** button

3. **Configure Credential**:
   - **Name**: `PostgreSQL Execution Results DB`
   - **Description**: `Database credentials for ansible-role-execution-result-update-db`
   - **Organization**: Select your organization
   - **Credential Type**: Choose one of the following:

#### Option 1: Using Machine Credential Type

For simple database authentication, use the built-in **Machine** credential type:

- **Credential Type**: Machine
- **Username**: `ansible_writer`
- **Password**: `your_secure_db_password`
- **Privilege Escalation Method**: Leave empty

#### Option 2: Creating a Custom Credential Type (Recommended)

For better control and additional fields, create a custom credential type:

1. **Navigate to Credential Types**: Go to **Administration** → **Credential Types**

2. **Create Custom Type**: Click **Add** and configure:

   **Name**: `Database Credential`
   
   **Input Configuration**:
   ```yaml
   fields:
     - id: db_host
       type: string
       label: Database Host
       help_text: Database server hostname or IP address
     - id: db_port
       type: string
       label: Database Port
       help_text: Database server port (default 5432 for PostgreSQL)
     - id: db_name
       type: string
       label: Database Name
       help_text: Name of the database
     - id: db_username
       type: string
       label: Database Username
       help_text: Database user for authentication
     - id: db_password
       type: string
       label: Database Password
       secret: true
       help_text: Database password (encrypted)
   required:
     - db_username
     - db_password
   ```

   **Injector Configuration**:
   ```yaml
   extra_vars:
     execution_result_db_host: '{{ db_host | default("localhost") }}'
     execution_result_db_port: '{{ db_port | default("5432") }}'
     execution_result_db_name: '{{ db_name | default("ansible_execution_results") }}'
     execution_result_db_user: '{{ db_username }}'
     execution_result_db_password: '{{ db_password }}'
   ```

3. **Create Credential Using Custom Type**:
   - Go back to **Resources** → **Credentials** → **Add**
   - **Name**: `PostgreSQL Execution Results DB`
   - **Credential Type**: `Database Credential` (your custom type)
   - Fill in the database details

#### Using Credentials in Job Templates

When configuring a Job Template that uses this role:

1. **Navigate to Job Template**: Go to **Resources** → **Templates** → Select your template

2. **Attach Credential**: In the **Credentials** section, click **Select** and choose your database credential

3. **Extra Variables**: You can override other settings if needed:
   ```yaml
   execution_result_db_type: "postgresql"
   execution_result_db_table_success: "success_jobs"
   execution_result_db_table_failed: "failed_jobs"
   ```

#### Benefits of AWX Credential Management

- **Security**: Passwords are encrypted in the database and never exposed in logs
- **Access Control**: Credentials can be restricted by user/team permissions
- **Auditing**: All credential usage is logged and auditable
- **Rotation**: Easy to update passwords without modifying playbooks
- **Separation of Concerns**: Developers don't need database passwords
- **Multi-Environment**: Use different credentials per inventory without code changes


## Troubleshooting

### No Results Found

If the role reports "No execution results found":

1. Verify `ansible-role-execution-result` ran before this role
2. Check the fact name: `execution_result_source_fact: "execution_results"`
3. Enable debug mode: `execution_result_debug_mode: true`

### Database Connection Failures

1. Verify database credentials
2. Check network connectivity to database host
3. Ensure required Python packages are installed
4. Check database server logs

### Missing Python Packages

Install required packages on the control node:

```bash
pip install psycopg2-binary  # PostgreSQL
pip install PyMySQL          # MySQL
pip install pymongo          # MongoDB
```
