# ansible-role-execution-result-update-db

Ansible role that captures execution results from [ansible-role-execution-result](https://github.com/Ansible-ServerAutomation/ansible-role-execution-result) and stores them in a database for persistent tracking, analytics, and auditing.

## Overview

This role consumes the artifacts generated by `ansible-role-execution-result` and stores them in various database backends including PostgreSQL, MySQL, SQLite, and MongoDB. It's designed to work seamlessly with AWX/Tower or standalone Ansible playbooks.

### Features

- **Multiple Database Support**: PostgreSQL, MySQL, SQLite, MongoDB
- **Dual-Table Design**: Separate tables for successful (`success_jobs`) and failed (`failed_jobs`) executions
- **Automatic Table Selection**: Routes records to the appropriate table based on return code (0 = success, ≠ 0 = failed)
- **Automatic Schema Management**: Creates database, tables, and indexes automatically
- **Batch Processing**: Efficient bulk inserts
- **Data Validation**: Validates data before insertion
- **Flexible Configuration**: Highly customizable through variables with sensible defaults
- **Error Handling**: Graceful failure handling with optional strict mode
- **AWX/Tower Integration**: Works with AWX artifacts and job metadata
- **Field Truncation**: Prevents database errors from oversized fields

### How It Works

The role automatically:
1. Creates the database `ansible_execution_results` if it doesn't exist
2. Creates two tables: `success_jobs` and `failed_jobs` with appropriate schemas
3. Reads execution results from the `execution_results` fact (set by `ansible-role-execution-result`)
4. Routes each record to the correct table based on return code:
   - **Return code = 0** → `success_jobs` table
   - **Return code ≠ 0** → `failed_jobs` table
5. Inserts records in batches for optimal performance
6. Creates indexes for efficient querying

**You don't need to specify table names or create schemas manually** - the role handles everything automatically using sensible defaults.

### Benefits of Dual-Table Design

- **Better Query Performance**: Queries on successful or failed jobs don't need to filter by status
- **Optimized Indexing**: Different indexes for success (playbook-focused) vs failure (error-focused) patterns
- **Simplified Analytics**: Easier to analyze failure patterns separately from success metrics
- **Storage Efficiency**: Failed jobs can store additional error details without impacting success table size

## Automatic Table Routing

The role automatically routes execution results to the appropriate table based on the task's return code:

| Return Code | Status | Target Table | Description |
|-------------|--------|--------------|-------------|
| `0` | SUCCESS | `success_jobs` | Task completed successfully |
| `!= 0` | FAILURE | `failed_jobs` | Task failed or returned error |
| N/A | UNKNOWN | `failed_jobs` | Status could not be determined |

### Complete Workflow Example

This example shows how execution results are automatically routed to the correct table:

```yaml
- name: Deploy Application with Automatic Result Tracking
  hosts: webservers
  gather_facts: true
  
  tasks:
    - name: Deploy application
      block:
        - name: Update code from Git
          ansible.builtin.git:
            repo: "https://github.com/example/app.git"
            dest: /var/www/app
          register: deploy_result

        - name: Record successful deployment
          ansible.builtin.include_role:
            name: ansible-role-execution-result
          vars:
            execution_result_registered_var: "{{ deploy_result }}"
            # If deploy_result has return_code = 0, this will be marked as SUCCESS

      rescue:
        - name: Record deployment failure
          ansible.builtin.include_role:
            name: ansible-role-execution-result
          vars:
            execution_result_registered_var: "{{ ansible_failed_result }}"
            # If deploy failed, return_code ≠ 0, this will be marked as FAILURE

      always:
        - name: Store all results in database (automatic table routing)
          ansible.builtin.include_role:
            name: ansible-role-execution-result-update-db
          vars:
            execution_result_db_password: "{{ vault_db_password }}"
            # Optional customization:
            execution_result_db_host: "{{ db_host | default('localhost') }}"
            execution_result_db_name: "ansible_automation"
            # Tables are auto-created and auto-routed:
            # - SUCCESS (return_code=0) → success_jobs table
            # - FAILURE (return_code≠0) → failed_jobs table
          run_once: true
          delegate_to: localhost
```

## Integration with ansible-role-execution-result

This role is designed to work with [ansible-role-execution-result](https://github.com/Ansible-ServerAutomation/ansible-role-execution-result). The typical workflow is:

1. **Execute tasks** in your playbook
2. **Capture results** using `ansible-role-execution-result` (sets the `execution_results` fact)
3. **Store in database** using this role (`ansible-role-execution-result-update-db`)

Example:

```yaml
- block:
    - name: Run critical task
      ansible.builtin.command: /usr/bin/critical_script.sh
      register: task_result
  
  rescue:
    - name: Capture failure
      ansible.builtin.include_role:
        name: ansible-role-execution-result
      vars:
        execution_result_registered_var: "{{ task_result }}"
  
  always:
    # Store captured results in database - automatic table routing
    - name: Persist to database
      ansible.builtin.include_role:
        name: ansible-role-execution-result-update-db
      vars:
        execution_result_db_password: "{{ vault_db_password }}"
        # Database and tables created automatically
        # Records routed to success_jobs or failed_jobs based on return_code
```

## Querying Results

Once data is stored, you can query the results from your database:

### Check Successful Jobs

```sql
-- PostgreSQL / MySQL
SELECT 
    timestamp,
    inventory_hostname,
    project,
    playbook,
    return_code,
    message
FROM success_jobs
ORDER BY timestamp DESC
LIMIT 10;
```

### Check Failed Jobs

```sql
-- PostgreSQL / MySQL
SELECT 
    timestamp,
    inventory_hostname,
    project,
    playbook,
    failed_task,
    failed_task_module,
    return_code,
    message,
    stderr
FROM failed_jobs
ORDER BY timestamp DESC
LIMIT 10;
```

### Count Success vs Failure by Project

```sql
-- PostgreSQL / MySQL
SELECT 
    'SUCCESS' as status,
    project,
    COUNT(*) as total
FROM success_jobs
GROUP BY project

UNION ALL

SELECT 
    'FAILURE' as status,
    project,
    COUNT(*) as total
FROM failed_jobs
GROUP BY project
ORDER BY project, status;
```

### Find Recent Failures for a Specific Playbook

```sql
-- PostgreSQL / MySQL
SELECT 
    timestamp,
    inventory_hostname,
    failed_task,
    return_code,
    message
FROM failed_jobs
WHERE playbook = 'deploy_application.yml'
  AND timestamp > NOW() - INTERVAL '7 days'
ORDER BY timestamp DESC;
```

## Security Considerations

### Password Management

**Never store database passwords in plain text!** Use Ansible Vault:

```bash
# Create encrypted variable file
ansible-vault create vars/db_secrets.yml

# Add password
execution_result_db_password: "your_secure_password"

# Use in playbook
ansible-playbook playbook.yml --ask-vault-pass
```

### SSL/TLS Connections

For production environments, enable SSL/TLS:

```yaml
execution_result_db_ssl_enabled: true
execution_result_db_ssl_ca_cert: "/path/to/ca.crt"
execution_result_db_ssl_client_cert: "/path/to/client.crt"
execution_result_db_ssl_client_key: "/path/to/client.key"
```

```yaml
Extra Variables:
  execution_result_db_type: "postgresql"
  execution_result_debug_mode: false
```

The database credentials will be automatically injected as extra variables by AWX/Tower, eliminating the need to store passwords in plain text or vault files.

## Troubleshooting

### No Results Found

If the role reports "No execution results found":

1. Verify `ansible-role-execution-result` ran before this role and set the `execution_results` fact
2. Check the fact name matches: `execution_result_source_fact: "execution_results"` (default)
3. Enable debug mode to see what data is available: `execution_result_debug_mode: true`
4. Check if AWX artifacts are available: `execution_result_source_artifacts: true` (default)

### Records Not Appearing in Expected Table

If records are in `failed_jobs` when you expect them in `success_jobs` (or vice versa):

1. Check the `return_code` field in the execution results:
   - `return_code = 0` → routed to `success_jobs`
   - `return_code ≠ 0` → routed to `failed_jobs`
2. Verify the task actually succeeded - some tasks may return non-zero codes even on success
3. Enable debug mode to see the routing: `execution_result_debug_mode: true`
4. Query both tables to confirm:
   ```sql
   SELECT COUNT(*), status FROM success_jobs GROUP BY status;
   SELECT COUNT(*), status FROM failed_jobs GROUP BY status;
   ```

### Database Connection Failures

1. Verify database credentials are correct
2. Check network connectivity to database host: `ping {{ execution_result_db_host }}`
3. Ensure required Python packages are installed on the control node
4. Check database server logs for authentication errors
5. Verify database user has CREATE and INSERT permissions

### Tables Not Created / Schema Errors

If tables aren't being created automatically:

1. Verify database user has CREATE TABLE permissions:
   ```sql
   -- PostgreSQL
   GRANT CREATE ON DATABASE ansible_execution_results TO ansible;
   ```
2. Check if tables already exist with different schemas - role uses `CREATE TABLE IF NOT EXISTS`
3. Enable query logging: `execution_result_log_queries: true`
4. Check database server error logs

### Missing Python Packages

Install required packages on the **control node** (where Ansible runs):

```bash
# PostgreSQL
pip install psycopg2-binary

# MySQL
pip install PyMySQL

# MongoDB
pip install pymongo

# SQLite (built-in, no package needed)
```
