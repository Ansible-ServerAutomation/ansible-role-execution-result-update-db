# ansible-role-execution-result-update-db

Ansible role that captures execution results from [ansible-role-execution-result](https://github.com/Ansible-ServerAutomation/ansible-role-execution-result) and stores them in a database for persistent tracking, analytics, and auditing.

## Overview

This role consumes the artifacts generated by `ansible-role-execution-result` and stores them in various database backends including PostgreSQL, MySQL, SQLite, and MongoDB. It's designed to work seamlessly with AWX/Tower or standalone Ansible playbooks.

**Important**: This role automatically delegates all tasks to `localhost` since database operations are performed from the control node where the role executes. The required Ansible collections are automatically installed on localhost if missing.

### Features

- **Multiple Database Support**: PostgreSQL, MySQL, SQLite, MongoDB
- **Dual-Table Design**: Separate tables for successful (`success_jobs`) and failed (`failed_jobs`) executions
- **Automatic Table Selection**: Routes records to the appropriate table based on return code (0 = success, ≠ 0 = failed)
- **Pre-requisite Verification**: Verifies database and tables exist before attempting inserts
- **Automatic Collection Installation**: Installs required Ansible collections on localhost if not present
- **Localhost Delegation**: All database operations run on localhost (control node)
- **Batch Processing**: Efficient bulk inserts
- **Data Validation**: Validates data before insertion
- **Flexible Configuration**: Highly customizable through variables with sensible defaults
- **Optional Runtime Driver Installation**: Can attempt to install missing Python database packages before running database tasks
- **Error Handling**: Graceful failure handling with optional strict mode
- **AWX/Tower Integration**: Works with AWX artifacts and job metadata
- **Field Truncation**: Prevents database errors from oversized fields

### How It Works

The role automatically:
1. **Delegates to localhost**: All tasks run on the control node (localhost) where database connectivity exists
2. **Installs required collections**: Checks if the appropriate Ansible collection (e.g., `community.mysql`) is installed on localhost, and installs it if missing
3. **Verifies Python packages**: Checks for required Python packages (psycopg2, PyMySQL, pymongo) on localhost and can optionally install missing ones
4. **Verifies the database**: Checks that the configured database (e.g., `ansible_execution_results`) exists
5. **Verifies tables**: Checks that both `success_jobs` and `failed_jobs` tables exist with appropriate schemas
6. **Reads execution results**: Reads from the `execution_results` fact (set by `ansible-role-execution-result`)
7. **Routes records**: Routes each record to the correct table based on return code:
   - **Return code = 0** → `success_jobs` table
   - **Return code ≠ 0** → `failed_jobs` table
8. **Inserts records**: Inserts records in batches for optimal performance

**You don't need to specify table names or install collections manually** - the role handles collection installation and table routing automatically. However, **you must create the database and tables beforehand** (see [Database Setup](#database-setup) for DDL scripts).

Depending on the database type, the following Python packages are required on the target host:

| Database | Required Package | Install Command |
|----------|-----------------|-----------------|
| PostgreSQL | psycopg2-binary | `pip install psycopg2-binary` |

The following Ansible collections are required based on your database type and will be **automatically installed on localhost** if not already present:

| Database | Required Collection | Status |
|----------|-------------------|---------|
| PostgreSQL | community.postgresql | ✅ Required for PostgreSQL operations |
| MySQL | community.mysql | ✅ Required for MySQL operations |
| MongoDB | community.mongodb | ✅ Required for MongoDB operations |
| SQLite | community.general | ✅ Required for SQLite operations |

**Installation**:
```bash
ansible-galaxy collection install community.postgresql
ansible-galaxy collection install community.mysql
ansible-galaxy collection install community.general
ansible-galaxy collection install community.mongodb
```

**For AWX/Tower Users**:

- The role will attempt to install collections at runtime if missing, but pre-installation is recommended.
- Python database drivers (psycopg2, PyMySQL, pymongo) must also be installed in the execution environment.

**For standalone Ansible**: The role will automatically check and install the required collection based on your database type.

## Python Interpreter Configuration

The role uses Python to execute database operations. By default, it uses `python3`, but you can configure a specific Python interpreter using the `execution_result_python_interpreter` variable.

## Python Package Installation

The role can optionally try to install missing Python database drivers before it runs connectivity checks or database tasks.

```yaml
execution_result_auto_install_packages: true
execution_result_package_install_method: "user"
```

Recommended usage:

- AWX/Tower: keep `execution_result_python_interpreter: "python3"` and pre-build the execution environment when possible.
- Standalone Ansible: point `execution_result_python_interpreter` at a virtual environment that already contains the database driver.
- Locked-down environments: set `execution_result_auto_install_packages: false` and rely on pre-installed packages only.

Detailed examples are in [docs/EXECUTION_ENVIRONMENT.md](docs/EXECUTION_ENVIRONMENT.md).

### Using a Virtual Environment

If you have installed database drivers (psycopg2, PyMySQL, pymongo) in a virtual environment on the Ansible control node or AWX localhost, configure the role to use that interpreter:

```yaml
- hosts: localhost
  vars:
    execution_result_python_interpreter: "/home/ubuntu/ansible_python_venv/bin/python"
    execution_result_db_type: postgresql
    execution_result_db_host: 10.0.0.14
    execution_result_db_password: "{{ vault_db_password }}"
  roles:
    - ansible-role-execution-result-update-db
```

### Using a Specific Python Version

You can also specify a specific Python version:

```yaml
execution_result_python_interpreter: "python3.11"
```

### Common Scenarios

| Scenario | Configuration Example |
|----------|----------------------|

### Benefits of Dual-Table Design

- **Better Query Performance**: Queries on successful or failed jobs don't need to filter by status
- **Optimized Indexing**: Different indexes for success (playbook-focused) vs failure (error-focused) patterns
- **Simplified Analytics**: Easier to analyze failure patterns separately from success metrics
- **Storage Efficiency**: Failed jobs can store additional error details without impacting success table size

## Automatic Table Routing

The role automatically routes execution results to the appropriate table based on the task's return code:

| Return Code | Status | Target Table | Description |
|-------------|--------|--------------|-------------|
| `0` | SUCCESS | `success_jobs` | Task completed successfully |
| `!= 0` | FAILURE | `failed_jobs` | Task failed or returned error |
| N/A | UNKNOWN | `failed_jobs` | Status could not be determined |

## Usage

### Minimal Configuration (Recommended)

The simplest way to use this role with all automatic defaults:

```yaml
- name: Store execution results with automatic table routing
  hosts: localhost
  gather_facts: true
  
  tasks:
    - name: Store results in database
      ansible.builtin.include_role:
        name: ansible-role-execution-result-update-db
      vars:
        # Only required variable - everything else uses defaults
        execution_result_db_password: "{{ vault_db_password }}"
        
        # Optional: Override database host if not localhost
        # execution_result_db_host: "db.example.com"
```

**What happens automatically:**
- Database `ansible_execution_results` is created (if it doesn't exist)
- Tables `success_jobs` and `failed_jobs` are created with proper schemas
- Records with return_code = 0 go to `success_jobs`
- Records with return_code ≠ 0 go to `failed_jobs`
- Batch inserts optimize performance
- Indexes are created for efficient querying

### Complete Workflow Example

This example shows how execution results are automatically routed to the correct table:

```yaml
- name: Deploy Application with Automatic Result Tracking
  hosts: webservers
  gather_facts: true
  
  tasks:
    - name: Deploy application
      block:
        - name: Update code from Git
          ansible.builtin.git:
            repo: "https://github.com/example/app.git"
            dest: /var/www/app
          register: deploy_result

        - name: Record successful deployment
          ansible.builtin.include_role:
            name: ansible-role-execution-result
          vars:
            execution_result_registered_var: "{{ deploy_result }}"
            # If deploy_result has return_code = 0, this will be marked as SUCCESS

      rescue:
        - name: Record deployment failure
          ansible.builtin.include_role:
            name: ansible-role-execution-result
          vars:
            execution_result_registered_var: "{{ ansible_failed_result }}"
            # If deploy failed, return_code ≠ 0, this will be marked as FAILURE

      always:
        - name: Store all results in database (automatic table routing)
          ansible.builtin.include_role:
            name: ansible-role-execution-result-update-db
          vars:
            execution_result_db_password: "{{ vault_db_password }}"
            # Optional customization:
            execution_result_db_host: "{{ db_host | default('localhost') }}"
            execution_result_db_name: "ansible_automation"
            # Tables are auto-created and auto-routed:
            # - SUCCESS (return_code=0) → success_jobs table
            # - FAILURE (return_code≠0) → failed_jobs table
          run_once: true
          delegate_to: localhost
```

## Integration with ansible-role-execution-result

This role is designed to work with [ansible-role-execution-result](https://github.com/Ansible-ServerAutomation/ansible-role-execution-result). The typical workflow is:

1. **Execute tasks** in your playbook
2. **Capture results** using `ansible-role-execution-result` (sets the `execution_results` fact)
3. **Store in database** using this role (`ansible-role-execution-result-update-db`)

Example:

```yaml
- block:
    - name: Run critical task
      ansible.builtin.command: /usr/bin/critical_script.sh
      register: task_result
  
  rescue:
    - name: Capture failure
      ansible.builtin.include_role:
        name: ansible-role-execution-result
      vars:
        execution_result_registered_var: "{{ task_result }}"
  
  always:
    # Store captured results in database - automatic table routing
    - name: Persist to database
      ansible.builtin.include_role:
        name: ansible-role-execution-result-update-db
      vars:
        execution_result_db_password: "{{ vault_db_password }}"
        # Database and tables must exist already
        # Records routed to success_jobs or failed_jobs based on return_code
```

## Querying Results

Once data is stored, you can query the results from your database:

### Check Successful Jobs

```sql
-- PostgreSQL / MySQL
SELECT 
    timestamp,
    inventory_hostname,
    project,
    playbook,
    return_code,
    message
FROM success_jobs
ORDER BY timestamp DESC
LIMIT 10;
```

### Check Failed Jobs

```sql
-- PostgreSQL / MySQL
SELECT 
    timestamp,
    inventory_hostname,
    project,
    playbook,
    failed_task,
    failed_task_module,
    return_code,
    message,
    stderr
FROM failed_jobs
ORDER BY timestamp DESC
LIMIT 10;
```

### Count Success vs Failure by Project

```sql
-- PostgreSQL / MySQL
SELECT 
    'SUCCESS' as status,
    project,
    COUNT(*) as total
FROM success_jobs
GROUP BY project

UNION ALL

SELECT 
    'FAILURE' as status,
    project,
    COUNT(*) as total
FROM failed_jobs
GROUP BY project
ORDER BY project, status;
```

### Find Recent Failures for a Specific Playbook

```sql
-- PostgreSQL / MySQL
SELECT 
    timestamp,
    inventory_hostname,
    failed_task,
    return_code,
    message
FROM failed_jobs
WHERE playbook = 'deploy_application.yml'
  AND timestamp > NOW() - INTERVAL '7 days'
ORDER BY timestamp DESC;
```

## Troubleshooting

### No Results Found

If the role reports "No execution results found":

1. Verify `ansible-role-execution-result` ran before this role and set the `execution_results` fact
2. Check the fact name matches: `execution_result_source_fact: "execution_results"` (default)
3. Enable debug mode to see what data is available: `execution_result_debug_mode: true`
4. Check if AWX artifacts are available: `execution_result_source_artifacts: true` (default)

### Records Not Appearing in Expected Table

If records are in `failed_jobs` when you expect them in `success_jobs` (or vice versa):

1. Check the `return_code` field in the execution results:
   - `return_code = 0` → routed to `success_jobs`
   - `return_code ≠ 0` → routed to `failed_jobs`
2. Verify the task actually succeeded - some tasks may return non-zero codes even on success
3. Enable debug mode to see the routing: `execution_result_debug_mode: true`
4. Query both tables to confirm:
   ```sql
   SELECT COUNT(*), status FROM success_jobs GROUP BY status;
   SELECT COUNT(*), status FROM failed_jobs GROUP BY status;
   ```

### Database Connection Failures

1. Verify database credentials are correct
2. Check network connectivity to database host: `ping {{ execution_result_db_host }}`
3. Ensure required Python packages are installed on the control node
4. Check database server logs for authentication errors
5. Verify database user has CREATE and INSERT permissions

### Database or Table Does Not Exist

**Error**: `Database 'ansible_execution_results' does not exist. Please create it before using this role.`
**Error**: `Table 'success_jobs' does not exist in database 'ansible_execution_results'. Please create it before using this role.`

**Cause**: The role requires that the database and tables already exist. It will not create them automatically.

**Solutions**:

1. **Create the database and tables** using the DDL scripts in [docs/DATABASE_SETUP.md](docs/DATABASE_SETUP.md)
2. **For PostgreSQL**: Use the automated setup script:
   ```bash
   python scripts/setup_postgresql_database.py --host DB_HOST --port 5432 --user DB_USER --password DB_PASSWORD --database ansible_execution_results
   ```
3. **Verify the database and tables exist**:
   ```sql
   -- PostgreSQL/MySQL
   SHOW DATABASES LIKE 'ansible_execution_results';
   USE ansible_execution_results;
   SHOW TABLES;
   
   -- SQLite
   sqlite3 /path/to/ansible_execution_results.db ".tables"
   
   -- MongoDB
   use ansible_execution_results
   show collections
   ```
4. **Check database name configuration** - ensure your variable matches the actual database name:
   ```yaml
   execution_result_db_name: "ansible_execution_results"
   ```

### Missing Python Packages

Install required packages on the **control node** (where Ansible runs):

```bash
# PostgreSQL
pip install psycopg2-binary

# MySQL
pip install PyMySQL

# MongoDB
pip install pymongo

# SQLite (built-in, no package needed)
```

### Missing Ansible Collections Error

**Error**: `couldn't resolve module/action 'community.postgresql.postgresql_query'` or similar collection module errors

**When This Occurs**:
- Collections are not pre-installed in AWX/Tower execution environments
- Collections are installed during playbook execution but not available in the current Ansible execution context
- Collection paths are not properly configured

**Solutions**:

1. **For AWX/Tower (Recommended)**: Pre-install collections in your execution environment (see [AWX Execution Environment Setup](#awx-execution-environment-setup))
   - This ensures collections are available before playbook execution
   - Avoids runtime installation and context issues

2. **For standalone Ansible**: Install collections before running the playbook:
   ```bash
  ansible-galaxy collection install community.postgresql community.mysql community.general community.mongodb
   ```

3. **If error persists after installation**: The collection may not be loaded in the current execution context. Try:
   - Re-run the playbook (collections installed in first run are available in subsequent runs)
   - Pre-install collections in your Ansible installation directory
   - For AWX: Rebuild your execution environment with collections included

4. **Quick verification**:
   ```bash
   ansible-galaxy collection list | grep community
   ```

**Note**: The role attempts to install missing collections automatically, but this may not make them immediately available. For production use, always pre-install collections in your execution environment.
